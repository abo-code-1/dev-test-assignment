## Задача 1. Распределение заказов

Сделано: исправлен баг с перепутанными координатами филиала в `findNearest`, добавлены правила `pickup_point` и `city`, дневной лимит, `POST /orders/:id/assign`, `GET /branches/:id/load`, закрыты все `test.todo`.

### Допущения

- Правила считаются только по активным филиалам своего магазина. Это относится и к `city`: закрытый филиал не считается филиалом в городе.
- `manual` не проверяет лимит, но занимает место: загрузка филиала может стать больше лимита, например 4 из 3.
- Запасной филиал при заполненном лимите ищется среди всех активных филиалов магазина и может оказаться в другом городе.
- Заказ без координат при заполненном филиале остаётся `unassigned`: ближайший посчитать не из чего.
- `unassigned` тоже запоминается: повторный вызов вернёт тот же результат, даже если места появятся. По заданию повтор возвращает то же распределение.
- При одновременно неверной дате и неизвестном филиале ответ `400`: дата проверяется первой.
- `GET /branches/:id/load` работает и для неактивного филиала.

### Несколько экземпляров с общей БД

Сейчас гарантии держатся на том, что `assignOrder` синхронный и работает в одном процессе. С несколькими экземплярами так не получится, проверка лимита и запись должны стать одной транзакцией:

- Идемпотентность: `assignments` с `order_id` как первичным ключом. Вставка через `INSERT ... ON CONFLICT DO NOTHING`, при конфликте читаем и возвращаем уже сохранённую строку.
- Лимит: таблица `branch_daily_load (branch_id, date, assigned)` и атомарный `UPDATE ... SET assigned = assigned + 1 WHERE assigned < limit`. Если обновилась 0 строк, филиал заполнен, переходим к следующему кандидату. `manual` обновляет счётчик без условия.
- Обе записи идут в одной транзакции, иначе упавший запрос оставит занятое место без распределения.
- Запасной филиал выбирается в цикле по кандидатам от ближнего к дальнему: другой экземпляр мог занять место между чтением и обновлением.
- Филиалы и заказы читаются из БД, а не из памяти на старте.
- Дату по Алматы стоит считать один раз и хранить в заказе, чтобы логика не разошлась между сервисами.
