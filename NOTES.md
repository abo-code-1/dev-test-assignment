### Несколько экземпляров с общей БД

Сейчас гарантии держатся на том, что `assignOrder` синхронный и работает в одном процессе. С несколькими экземплярами так не получится, проверка лимита и запись должны стать одной транзакцией:

- Идемпотентность: `assignments` с `order_id` как первичным ключом. Вставка через `INSERT ... ON CONFLICT DO NOTHING`, при конфликте читаем и возвращаем уже сохранённую строку.
- Лимит: таблица `branch_daily_load (branch_id, date, assigned)` и атомарный `UPDATE ... SET assigned = assigned + 1 WHERE assigned < limit`. Если обновилась 0 строк, филиал заполнен, переходим к следующему кандидату. `manual` обновляет счётчик без условия.
- Обе записи идут в одной транзакции, иначе упавший запрос оставит занятое место без распределения.
- Запасной филиал выбирается в цикле по кандидатам от ближнего к дальнему: другой экземпляр мог занять место между чтением и обновлением.
- Филиалы и заказы читаются из БД, а не из памяти на старте.
- Дату по Алматы стоит считать один раз и хранить в заказе, чтобы логика не разошлась между сервисами.

## Задача 2. Онлайн-запись

Сделано: исправлен `overlaps`, дописан `getSlots`, добавлены `GET /masters/:id/slots`, `POST /bookings`, `DELETE /bookings/:id`, закрыты все `test.todo`, есть тест на одновременное бронирование.

### Допущения

- Слот в точности в текущий момент уже не выдаётся: по заданию начало должно быть позже текущего момента.
- Порядок проверок в `GET slots` и `POST /bookings`: сначала формат запроса (`400`), затем существование мастера и услуги (`404`), затем то, что мастер оказывает услугу (`400`), и только потом слот (`409`). Сочетание «мастер не оказывает услугу» в `POST` даёт `400`, как в `GET slots`.
- Для несуществующего мастера или услуги в `POST /bookings` ответ `404`: в задании это не описано, взято по аналогии с `GET slots`.
- `start` без часового пояса — `400`, иначе время зависело бы от пояса сервера. Время не по шагу слотов или с секундами — `409`.
- Мобильными считаются коды 70x, 747, 75x, 76x и 77x, городские номера вроде `+7 727 ...` отклоняются. Кроме `+7` и `8` принимается запись с `7` без плюса, номер без кода страны отклоняется.
- Отменить ровно за 2 часа можно: запрет только на «меньше чем за 2 часа». Уже прошедшую запись отменить нельзя.

### Одновременные бронирования с PostgreSQL

Сейчас от гонки защищает очередь на мастера в `lock.ts`. Она живёт в памяти одного процесса, поэтому с несколькими экземплярами не работает, и гарантию должна дать сама база.

Основной вариант — ограничение-исключение. Оно проверяет именно пересечение интервалов, поэтому покрывает услуги разной длины:

```sql
CREATE EXTENSION btree_gist;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at) WITH &&)
  WHERE (status = 'active');
```

Диапазон `tstzrange` по умолчанию полуоткрытый, поэтому записи встык не конфликтуют, как и в `overlaps`. Условие `WHERE` не даёт отменённым записям мешать. Приложение делает `INSERT` и на ошибку `23P01` (`exclusion_violation`) отвечает `409 slot_unavailable`. Проверка слота через `getSlots` остаётся для графика, перерывов и прошедшего времени, а гонку закрывает ограничение.

Обычный уникальный индекс по `(master_id, start_at)` не подойдёт: он не поймает пересечение записей с разным началом.

Если логика станет сложнее одного ограничения, можно брать `pg_advisory_xact_lock` по мастеру или `SELECT ... FOR UPDATE` по строке мастера и держать проверку со вставкой в одной транзакции. Это та же очередь на мастера, что и сейчас, но на стороне базы. Ограничение всё равно стоит оставить как последнюю защиту.

Отмену стоит делать одним запросом `UPDATE ... WHERE status = 'active' AND start_at - now() >= interval '2 hours'`. Время при этом берётся из одного источника, а не с часов разных экземпляров.
